# 平台路由

平台不是交付前的排版选项，而是大纲之前的写作约束。先选平台，再选文章原型，最后决定标题、段落、列表、链接和产品出现方式。

## 三个规范化平台

| Platform ID | 读者正在做什么 | 默认交付 | 核心成功信号 |
|---|---|---|---|
| `zhihu` | 判断一个观点或方案是否值得采纳 | `article.md` | 论点推进自然，能解释机制、权衡并给出决策动作 |
| `github` | 理解仓库、复现操作或核对技术决策 | `README.md` 或 `docs/<slug>.md` | 读者能快速知道用途、边界和第一次成功操作 |
| `seo-blog` | 带着搜索问题寻找完整、可信的答案 | `article.md` + 元数据 | 搜索意图被满足，页面可发现且不用二次搜索补齐关键答案 |

“GitHub 文章”不是一个单一文体。根据仓库上下文选择 README、操作指南、架构说明或基准/决策记录。没有仓库上下文时，默认交付可放入 `docs/` 的技术指南，不虚构安装命令、项目结构或测试结果。

## 选择顺序

1. 用户明确指定平台时直接采用，并记录 `Platform ID`。
2. 用户指定 `README`、仓库首页、快速开始时选 `github`。
3. 用户指定关键词、搜索意图、meta description、内容集群时选 `seo-blog`。
4. 用户指定知乎回答、知乎专栏、第三方技术软文时选 `zhihu`。
5. 平台未指定但任务是 99CDN 第三方软文时，保守默认 `zhihu`，并在 Brief 中明示；若输出路径或商业方式会因此实质改变，先询问。

每次只加载一个平台适配器：

- `zhihu`：读取 [知乎适配器](zhihu-style.md)
- `github`：读取 [GitHub 适配器](github-style.md)
- `seo-blog`：读取 [SEO 博客适配器](seo-blog-style.md)

三者都必须读取 [人工编辑层](human-editing.md)。不要把三个适配器的规则叠加到同一篇文章。

## 先选文章原型

平台内部也不能只有一个模板。根据读者任务选择一个主原型：

| 平台 | 可选原型 |
|---|---|
| 知乎 | 决策分析、问题诊断、机制解释、观点纠偏 |
| GitHub | 项目 README、操作指南、架构说明、基准或决策记录 |
| SEO 博客 | 常青问题指南、方案比较、实施前评估、故障/成本诊断 |

原型决定信息顺序，不规定固定标题文案或章节数量。只有内容关系复杂时才增加层级；不得为了“像平台”而补空泛章节。

## 冲突处理

- 平台约定与事实安全冲突时，事实安全优先。
- SEO 与知乎可读性冲突时，保留自然表达，把关键词放到标题、摘要或真正相关的小标题，不机械重复。
- 软广要求与 GitHub 仓库用途冲突时，将产品写成实现选项、兼容项或赞助披露，不把 README 改成推广文章。
- 用户给出的格式优先于默认平台轮廓，但要指出会损害可读性、复现性或披露要求的冲突。

## 完成检查

交付前只看标题和结构块，确认它们属于所选平台：

- 知乎：标题串起来能复述推理，而不是说明书目录。
- GitHub：首屏能回答项目是什么、为何有用、下一步做什么。
- SEO 博客：标题、摘要、开头和主要章节服务同一个搜索意图。
