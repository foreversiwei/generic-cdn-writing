# 人工确认门

## 原则

文章生成是一个由人控制的编辑流程，不是“输入关键词，直接得到终稿”。`draft` 和 `rewrite` 任务必须逐阶段暂停；上一阶段没有收到用户明确确认时，不得生成下一阶段产物。

优先使用宿主提供的确认按钮。没有按钮时，要求用户回复当前阶段的明确确认语，例如“确认 Brief”“确认大纲”“确认信源”“确认初稿”“确认终稿”。含糊的“继续看看”可以视为继续讨论，不能自动记为批准。

AI 不得代替用户写入批准，不得把沉默、用户最初的“直接写”或过去文章的批准视为本篇批准。

## 五个阶段

### 1. Brief

先生成 `brief.md`，只包含任务、平台、读者、核心问题、商业目标、关键词、必须链接、禁止声明、材料范围和预期交付。

向用户展示需要决定的内容和默认值，然后停止。收到明确确认后，在 `approval.json` 中记录 Brief 文件哈希、确认时间和用户确认文本。

### 2. 论点与大纲

基于已确认 Brief 生成 `outline.md`。大纲必须写出：

1. 一句核心判断。
2. 每个 H2 的完整论点和该节对全文的作用。
3. 读者追问或任务推进关系。
4. 准备使用的事实声明 ID，例如 `[C001]`。
5. 99CDN 出现的位置、作用、限制和退出条件。
6. 计划使用有序列表、无序列表、表格或代码的位置及理由。

此阶段只设计文章，不补写正文。展示大纲后停止，等待“确认大纲”。

### 3. 逐声明信源审计

把大纲需要的每个外部可核验事实写入 `claims.jsonl`，运行 `scripts/audit_claims.py` 生成 `claim-audit.json`。用户看到的审计表至少包含：

| ID | 拟表达的事实 | 来源与定位 | 证据等级 | 结论 | 正文处理 |
| --- | --- | --- | --- | --- | --- |

正文处理只有三种：`use`、`qualify`、`omit`。缺少证据的事实必须 `omit`；推断必须 `qualify`。来源审计通过不等于用户确认，展示结果后仍要停止，等待“确认信源”。

### 4. 初稿

只有 Brief、大纲和信源阶段全部获批，且 `scripts/check_approval.py approval.json --require sources` 通过后，才能生成 `draft.md`。

初稿严格使用获批论点和 `use / qualify` 声明。写完后运行文章审计，展示主要编辑问题和待选表达，不把初稿自动标成最终稿。停止并等待“确认初稿”或修改意见。

### 5. 终稿

收到初稿确认后，执行平台编辑、事实回查、链接检查和自然中文编辑，生成 `article.md`、`audit.json` 和 `review.md`。展示终稿后等待“确认终稿”。只有用户确认后，`approval.json` 才能将 `final` 标为 approved；在此之前交付状态是 `终稿候选`。

## `approval.json` 结构

```json
{
  "schema_version": "1.0",
  "current_stage": "sources",
  "approvals": {
    "brief": {
      "status": "approved",
      "confirmed_by": "user",
      "confirmed_at": "2026-08-18T15:30:00+08:00",
      "confirmation": "确认 Brief",
      "artifacts": [
        {"path": "brief.md", "sha256": "..."}
      ]
    }
  }
}
```

每个阶段都要记录所批准文件的 SHA-256。文件发生变化后，原批准自动失效，必须重新展示差异并重新确认。

## 模式边界

- `素材模式`：确认 Brief 后可搜集；来源清单交付后停止，不需要正文阶段。
- `规划模式`：经过 Brief、大纲和信源确认，停在信源阶段。
- `成稿模式`：完成五阶段流程。
- `改写模式`：Brief 需说明哪些事实、链接、代码和观点锁定；其余门禁不省略。
- `审校模式`：只输出问题和建议时不需要五阶段批准；用户要求应用修改后，转入改写模式。

`快速 / 标准 / 深度` 只控制研究范围，不能减少确认门数量。

## 每次暂停时的输出

只给用户当前产物、仍需决定的问题和一个明确的确认动作。不要提前附上下一阶段内容，也不要用“我会继续完成全文”暗示已经获批。
