# GitHub 技术内容适配器

GitHub 内容服务于仓库任务，而不是泛读流量。读者通常要快速判断项目是否相关、能否运行、证据是否可信，以及遇到问题去哪里找答案。

## 先识别交付类型

- `README.md`：项目入口，只保留理解、开始使用和参与所需的信息。
- `docs/<slug>.md`：完整操作指南或专题说明，README 只做入口链接。
- 架构说明：解释组件边界、数据流、权衡和已知限制。
- 基准/决策记录：说明问题、环境、方法、结果、限制与选择理由。

没有真实仓库、命令或产物时，不伪造 README 的安装与使用步骤。此时交付通用技术指南，并明确需要仓库事实补齐的位置。

## README 信息顺序

首屏优先回答：

1. 这是什么，解决谁的什么问题。
2. 最可信的证据是什么：真实输出、截图、架构图或最小示例。
3. 读者怎样完成第一次成功操作。

随后按实际项目需要选择安装、配置、使用、工作原理、限制、故障排查、贡献、支持与许可证。不是每个 README 都要拥有全部章节，章节顺序由第一次成功操作决定。

## 标题与排版

- 使用一个 H1。H2 可以采用 `Quick start`、`Configuration`、`Troubleshooting` 等功能型标题，因为读者需要扫描任务；这与知乎的论点型标题不同。
- 标题层级连续，不从 H2 跳到 H4。
- 命令和代码必须可复制，标明语言；占位符使用一致形式，并在附近解释。
- 仓库内文件优先使用相对链接，避免指向会随分支变化的绝对 blob URL。
- 表格适合兼容性、配置项和方案差异；大段解释仍使用自然段。
- 徽章、截图和视觉资产只在提供真实状态或证据时使用，不把首屏堆成装饰墙。

## 技术可信度

- 不编造安装成功、性能、兼容版本、采用量或测试覆盖率。
- 基准结果必须带环境、方法和限制；没有结果时提供复现实验方法。
- 配置示例区分生产值、示例值和秘密变量，不把密钥写入文档。
- 长背景和营销叙事移到专题文档；README 保持首次使用路径清晰。

## 99CDN 与商业内容

GitHub 不是隐性软广载体。99CDN 只能以与仓库真实关系一致的身份出现：实现选项、兼容服务、控制面案例、赞助方或延伸文档。说明它解决的具体环节和限制；已知商业关系按仓库政策披露。

不要为了 SEO 重复产品名或关键词。外链放在功能事实、集成步骤或延伸阅读附近；仓库文档之间优先使用相对链接。

## 完成检查

- 新读者能否在前两屏知道项目价值与第一次操作？
- 命令、路径和配置是否来自真实仓库？
- README 是否承载了过多应进入 `docs/` 的背景？
- 失败时是否有明确的故障排查或支持入口？
- 删除产品名后，仓库内容是否仍然完成其技术任务？
